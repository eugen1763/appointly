A bounded `tabTo` helper may inspect `document.activeElement`, but it must not call `focus`, `click`, `fill`, `check`, `selectOption`, or DOM event dispatch.

Parse `putResponseSuccessSchema`, require a higher revision, wait for the exact mobile guest/option ledger value to become Yes and for `Saved`. Tab to the first visible mobile card summary, press Enter, require it expanded, and require the exact participant response text inside the card.
5. At each mobile keyboard stop above, prove the target is `document.activeElement`. For the name input, Join button, checked Unanswered radio, keyboard-activated Yes radio, and card summary, require a visible focus indicator from computed `outline`, `box-shadow`, or text decoration before typing or activating the next control.

8. Read final schema-validated snapshots from both pages. Require the exact final revision from the desktop save, both participant identities and names exactly once, both original option identities, the mobile guest's Yes only on option one, the desktop guest's No only on option two, unchanged date semantics, and correct viewer identity per context. Require zero pointer observations again.

## Keyboard and layout boundary

The public guest flows must not use any pointer or programmatic focus/action API. Native sequential focus navigation uses `Tab` and `Shift+Tab`; native radio-group selection uses only the minimal `ArrowLeft`, `ArrowRight`, `ArrowUp`, or `ArrowDown` movement needed from the checked Unanswered radio. The owner creation helper is outside the keyboard-only public-page boundary. Locator queries, response waits, schema parsing, layout inspection, and snapshot GETs are allowed. Use no screenshots as assertions, sleeps, fixed public IDs, direct creation or mutation APIs, database access, production edits, unrelated flows, browser commands, or commits.

Skip formatter, linter, TypeScript, build, browser commands, all tests, and commits. Record implementation and pending coordinator validation in the report.
